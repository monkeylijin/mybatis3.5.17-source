### 一、选择题

**1. 下列哪个不是 SqlNode 的实现类？**

A. IfSqlNode  
B. ForEachSqlNode  
C. DynamicSqlSource  
D. WhereSqlNode

<details>
<summary>查看答案</summary>

**答案：C**

**解析**：DynamicSqlSource 是 SqlSource 的实现类，不是 SqlNode 的实现类。SqlNode 的实现类包括：IfSqlNode、ForEachSqlNode、WhereSqlNode、TrimSqlNode、ChooseSqlNode 等。
</details>

**2. `<foreach>` 生成的额外参数前缀是？**

A. `_frch_`  
B. `__frch_`  
C. `foreach_`  
D. `__foreach_`

<details>
<summary>查看答案</summary>

**答案：B**

**解析**：ForEachSqlNode 使用 `__frch_` 作为额外参数的前缀，例如 `__frch_id_0`、`__frch_id_1` 等。这是源码中定义的常量 `ITEM_PREFIX = "__frch_"`。
</details>

**3. DynamicContext 的主要作用是？**

A. 解析XML配置  
B. 收集SQL片段和绑定参数  
C. 执行SQL语句  
D. 处理结果集

<details>
<summary>查看答案</summary>

**答案：B**

**解析**：DynamicContext 是动态SQL生成过程中的上下文对象，主要用于：
1. 收集各个 SqlNode 生成的SQL片段
2. 绑定参数（包括额外参数）
3. 提供OGNL求值所需的上下文环境
</details>

**4. 以下哪个标签不需要OGNL表达式求值？**

A. `<if test="...">`  
B. `<where>`  
C. `<foreach collection="...">`  
D. `<bind value="...">`

<details>
<summary>查看答案</summary>

**答案：B**

**解析**：`<where>` 标签本质是 TrimSqlNode，不需要OGNL表达式求值。其他选项都需要：
- `<if>` 需要求值 test 属性
- `<foreach>` 需要求值 collection 属性
- `<bind>` 需要求值 value 属性
</details>

**5. 关于动态SQL的性能，下列说法正确的是？**

A. 动态SQL比静态SQL性能更好  
B. 动态SQL每次都要重新解析  
C. 动态SQL与静态SQL性能相同  
D. 动态SQL的解析结果会被缓存

<details>
<summary>查看答案</summary>

**答案：B**

**解析**：DynamicSqlSource 每次执行都要：
1. 创建 DynamicContext
2. 遍历 SqlNode 树
3. 应用每个节点生成SQL
4. 解析 `#{}` 占位符

而 RawSqlSource 在构建期就完成了解析，运行期直接返回，性能差距可达 10-20 倍。
</details>

### 二、判断题

**1. `<where>` 标签会自动去除开头的 AND 或 OR。**

<details>
<summary>查看答案</summary>

**答案：✅ 正确**

**解析**：WhereSqlNode 继承自 TrimSqlNode，配置了 `prefixOverrides = ["AND ", "OR ", ...]`，会自动去除子节点生成的 SQL 开头的 AND 或 OR。
</details>

---

**2. `<set>` 标签会自动去除开头的逗号。**

<details>
<summary>查看答案</summary>

**答案：❌ 错误**

**解析**：`<set>` 标签去除的是**结尾**的逗号，不是开头。SetSqlNode 配置了 `prefixOverrides = [","]` 和 `suffixOverrides = [","]`，主要作用是去除最后一个 `SET` 项后面的逗号。
</details>

---

**3. OGNL表达式可以调用静态方法。**

<details>
<summary>查看答案</summary>

**答案：✅ 正确**

**解析**：OGNL 支持调用静态方法，语法为 `@全限定类名@方法名(参数)`，例如：
```xml
<bind name="max" value="@java.lang.Math@max(a, b)"/>
```
</details>

---

**4. `<foreach>` 遍历 Map 时，item 对应的是 Map.Entry。**

<details>
<summary>查看答案</summary>

**答案：✅ 正确**

**解析**：当 `<foreach>` 遍历 Map 时，实际遍历的是 `map.entrySet()`，item 绑定的是 `Map.Entry` 对象。可以通过 `item.key` 和 `item.value` 访问键值。
</details>

---

**5. 使用 `${}` 和 `#{}` 的安全性相同。**

<details>
<summary>查看答案</summary>

**答案：❌ 错误**

**解析**：
- `#{}` 使用 PreparedStatement，参数会被正确转义，**安全**
- `${}` 是字符串替换，直接拼接到SQL，**有SQL注入风险**

应该尽量使用 `#{}`，只在必须动态拼接SQL结构（如表名、列名）时才使用 `${}`，并做好参数校验。
</details>

### 四、简答题

**1. 简述 DynamicSqlSource 的完整执行流程。**

<details>
<summary>查看参考答案</summary>

**参考答案**：

1. **创建动态上下文**
   ```java
   DynamicContext context = new DynamicContext(configuration, parameterObject);
   ```

2. **应用 SqlNode 树**
   ```java
   rootSqlNode.apply(context);
   ```
   - 遍历树结构
   - 每个节点根据条件生成SQL片段
   - 通过 `context.appendSql(...)` 收集
   - 通过 `context.bind(...)` 绑定参数

3. **解析占位符**
   ```java
   SqlSourceBuilder sqlSourceParser = new SqlSourceBuilder(configuration);
   SqlSource sqlSource = sqlSourceParser.parse(context.getSql(), parameterType, context.getBindings());
   ```
   - 将 `#{}` 替换为 `?`
   - 生成 ParameterMapping 列表

4. **获取 BoundSql**
   ```java
   BoundSql boundSql = sqlSource.getBoundSql(parameterObject);
   ```

5. **复制额外参数**
   ```java
   context.getBindings().forEach((key, value) -> {
       boundSql.setAdditionalParameter(key, value);
   });
   ```

**关键点**：每次调用都要完整执行以上流程，这是动态SQL性能开销的主要原因。
</details>

---

**2. 为什么需要额外参数（additionalParameters）？直接使用原参数不行吗？**

<details>
<summary>查看参考答案</summary>

**参考答案**：

**需要额外参数的原因**：

1. **`<foreach>` 迭代变量冲突**
   ```xml
   <foreach collection="users" item="user">
       #{user.name}  <!-- 每次迭代 user 都是不同的对象 -->
   </foreach>
   ```
   如果不重命名，ParameterHandler 无法区分每次迭代的 `user`。

2. **参数命名唯一性**
   ```java
   // 生成的额外参数
   __frch_user_0 = users.get(0)
   __frch_user_1 = users.get(1)
   // ...
   ```

3. **`<bind>` 计算结果存储**
   ```xml
   <bind name="pattern" value="'%' + name + '%'"/>
   ```
   计算结果需要存储到某个地方，additionalParameters 就是用来存储这些临时变量的。

4. **嵌套查询参数传递**
   ```xml
   <association property="user" column="user_id" select="findUserById"/>
   ```
   父查询的 `user_id` 列值需要传递给子查询，通过额外参数实现。

**如果不使用额外参数**：
- `<foreach>` 无法正确展开
- `<bind>` 无法存储计算结果
- 参数绑定会混乱
</details>

**3. 对比分析 `<if>`、`<choose>` 和 Java 代码拼接 SQL 的优劣。**

<details>
<summary>查看参考答案</summary>

**参考答案**：

| 维度 | 动态标签 | Java代码拼接 |
|------|---------|------------|
| **可读性** | ✅ 优秀：SQL结构清晰 | ❌ 较差：SQL与逻辑混杂 |
| **维护性** | ✅ 优秀：集中管理 | ❌ 较差：分散在代码中 |
| **类型安全** | ⚠️ 一般：运行期检查 | ✅ 优秀：编译期检查 |
| **性能** | ⚠️ 较低：每次解析 | ✅ 较高：提前拼接 |
| **灵活性** | ⚠️ 受限于标签能力 | ✅ 完全灵活 |
| **SQL注入风险** | ✅ 低（用`#{}`） | ⚠️ 高（需手动防范） |
| **测试难度** | ✅ 容易：独立测试 | ❌ 困难：依赖环境 |

**推荐策略**：
- **简单条件**：使用 `<if>`
- **多分支选择**：使用 `<choose>`
- **复杂逻辑**：使用 `@SelectProvider`
- **性能关键**：拆分多个静态SQL

**示例对比**：

```xml
<!-- 动态标签 -->
<select id="findUsers" resultType="User">
    SELECT * FROM user
    <where>
        <if test="name != null">AND name = #{name}</if>
        <if test="age != null">AND age > #{age}</if>
    </where>
</select>
```

```java
// Java代码拼接
public List<User> findUsers(String name, Integer age) {
    StringBuilder sql = new StringBuilder("SELECT * FROM user WHERE 1=1");
    List<Object> params = new ArrayList<>();
    
    if (name != null) {
        sql.append(" AND name = ?");
        params.add(name);
    }
    if (age != null) {
        sql.append(" AND age > ?");
        params.add(age);
    }
    
    return jdbcTemplate.query(sql.toString(), params.toArray(), rowMapper);
}
```
</details>

**4. 如何优化包含大量 `<if>` 标签的动态SQL？**

<details>
<summary>查看参考答案</summary>

**参考答案**：

**优化策略**：

**策略1：拆分多个静态SQL**

```xml
<!-- ❌ 不推荐：复杂动态SQL -->
<select id="findUsers" resultType="User">
    SELECT * FROM user
    <where>
        <if test="name != null">AND name = #{name}</if>
        <if test="email != null">AND email = #{email}</if>
        <if test="minAge != null">AND age >= #{minAge}</if>
        <if test="maxAge != null">AND age <= #{maxAge}</if>
        <if test="status != null">AND status = #{status}</if>
        <if test="createdAfter != null">AND created_at >= #{createdAfter}</if>
        <if test="createdBefore != null">AND created_at <= #{createdBefore}</if>
    </where>
</select>

<!-- ✅ 推荐：拆分为多个方法 -->
<select id="findByName" resultType="User">
    SELECT * FROM user WHERE name = #{name}
</select>

<select id="findByNameAndAge" resultType="User">
    SELECT * FROM user WHERE name = #{name} AND age BETWEEN #{minAge} AND #{maxAge}
</select>
```

**策略2：使用 `@SelectProvider`**

```java
public class UserSqlProvider {
    private static final Map<String, String> SQL_CACHE = new ConcurrentHashMap<>();
    
    public String findUsers(Map<String, Object> params) {
        // 生成缓存键
        String cacheKey = generateCacheKey(params);
        
        // 从缓存获取
        return SQL_CACHE.computeIfAbsent(cacheKey, k -> buildSql(params));
    }
    
    private String buildSql(Map<String, Object> params) {
        StringBuilder sql = new StringBuilder("SELECT * FROM user WHERE 1=1");
        
        if (params.get("name") != null) {
            sql.append(" AND name = #{name}");
        }
        // ... 其他条件
        
        return sql.toString();
    }
}
```

**策略3：限制动态范围**

```xml
<!-- 只在必要的地方使用动态SQL -->
<select id="findUsers" resultType="User">
    SELECT * FROM user
    WHERE status = 'ACTIVE'  <!-- 固定条件 -->
    <if test="name != null">
        AND name = #{name}  <!-- 动态条件 -->
    </if>
</select>
```

**策略4：使用索引优化**

```sql
-- 为常用查询条件创建组合索引
CREATE INDEX idx_user_name_age ON user(name, age);
```

**性能对比**：

```
复杂动态SQL（7个<if>）：~500,000 ops/sec
拆分静态SQL：            ~10,000,000 ops/sec
@SelectProvider+缓存：   ~5,000,000 ops/sec
```
</details>

**5. `<foreach>` 处理大集合（10000个元素）时可能遇到什么问题？如何解决？**

<details>
<summary>查看参考答案</summary>

**参考答案**：

**可能遇到的问题**：

1. **SQL语句过长**
   - Oracle：4000字符限制
   - MySQL：`max_allowed_packet` 限制（默认4MB）
   - 示例：`IN (?, ?, ..., ?)` 10000个占位符

2. **PreparedStatement 参数过多**
   - 某些数据库有参数数量限制
   - 例如：Oracle 最多1000个参数

3. **性能问题**
   - 动态SQL生成耗时
   - 大量参数绑定耗时
   - 数据库执行计划不优

4. **内存占用**
   - BoundSql.additionalParameters 膨胀
   - ParameterMapping 列表过长

**解决方案**：

**方案1：分批处理（推荐）**

```java
public List<User> findByIds(List<Long> ids) {
    int batchSize = 1000;
    List<User> results = new ArrayList<>();
    
    for (int i = 0; i < ids.size(); i += batchSize) {
        int end = Math.min(i + batchSize, ids.size());
        List<Long> batch = ids.subList(i, end);
        results.addAll(userMapper.findByIdsBatch(batch));
    }
    
    return results;
}
```

**方案2：临时表**

```java
// 1. 创建临时表
session.update("createTempTable");

// 2. 插入ID到临时表
session.update("insertToTempTable", ids);

// 3. JOIN临时表查询
List<User> users = session.selectList("findByTempTable");

// 4. 清理临时表
session.update("dropTempTable");
```

**方案3：使用EXISTS子查询**

```xml
<select id="findByIds" resultType="User">
    SELECT * FROM user u
    WHERE EXISTS (
        SELECT 1 FROM (
            <foreach collection="ids" item="id" open="SELECT " separator=" UNION ALL SELECT ">
                #{id} as id
            </foreach>
        ) t WHERE t.id = u.id
    )
</select>
```

**方案4：程序分批+缓存合并**

```java
@Cacheable(key = "'users:' + #ids.toString()")
public List<User> findByIds(List<Long> ids) {
    return batchProcess(ids, 1000, userMapper::findByIdsBatch);
}
```

**性能对比**（10000个ID）：

| 方案 | 耗时 | 内存 | 说明 |
|------|------|------|------|
| 单次IN查询 | 500ms | 高 | 可能超限 |
| 分批10次 | 200ms | 中 | **推荐** |
| 临时表 | 150ms | 低 | 适合大数据量 |
| EXISTS子查询 | 600ms | 高 | 不推荐 |
</details>

## 📝 知识点总结

### 核心架构

```
动态SQL生成流程:

MappedStatement.getBoundSql(param)
    ↓
DynamicSqlSource.getBoundSql(param)
    ↓
1. new DynamicContext(config, param)
    ↓
2. rootSqlNode.apply(context)
    ├── IfSqlNode: 条件判断
    ├── ForEachSqlNode: 循环遍历
    ├── TrimSqlNode: 前后缀处理
    └── StaticTextSqlNode: 静态文本
    ↓
3. SqlSourceBuilder.parse(sql, type, bindings)
    ├── 解析 #{} → ?
    └── 生成 ParameterMapping
    ↓
4. new BoundSql(sql, parameterMappings, parameterObject)
    ↓
5. 复制 additionalParameters
    ↓
返回 BoundSql
```

### 关键类图

```
SqlSource 体系:
- SqlSource (接口)
  ├── StaticSqlSource (纯静态)
  ├── RawSqlSource (静态+占位符)
  └── DynamicSqlSource (动态)

SqlNode 体系:
- SqlNode (接口)
  ├── StaticTextSqlNode (静态文本)
  ├── MixedSqlNode (混合节点)
  ├── IfSqlNode (<if>)
  ├── TrimSqlNode (<trim>)
  │   ├── WhereSqlNode (<where>)
  │   └── SetSqlNode (<set>)
  ├── ForEachSqlNode (<foreach>)
  ├── ChooseSqlNode (<choose>)
  └── VarDeclSqlNode (<bind>)
```

### 常用标签对比

| 标签 | 作用 | 使用场景 | 性能 |
|------|------|---------|------|
| `<if>` | 条件判断 | 可选条件 | 快 |
| `<where>` | WHERE子句 | 多个可选AND条件 | 快 |
| `<set>` | SET子句 | 动态UPDATE | 快 |
| `<foreach>` | 循环遍历 | IN子句、批量操作 | 慢（大集合） |
| `<choose>` | 多分支 | 互斥条件 | 中 |
| `<trim>` | 前后缀处理 | 自定义拼接规则 | 快 |
| `<bind>` | 变量绑定 | 复杂表达式 | 快 |

### 性能对比

| SqlSource类型 | 解析时机 | 运行期开销 | 性能 | 适用场景 |
|--------------|---------|-----------|------|---------|
| StaticSqlSource | 构建期 | 无 | ⭐⭐⭐⭐⭐ | 纯静态SQL |
| RawSqlSource | 构建期 | 极低 | ⭐⭐⭐⭐⭐ | 静态SQL+占位符 |
| DynamicSqlSource | 运行期 | 高 | ⭐⭐ | 动态条件 |

**性能数据**（ops/sec）：
- RawSqlSource: ~10,000,000
- DynamicSqlSource: ~500,000
- **差距**: 约20倍

### 最佳实践清单

✅ **推荐做法**：
- [ ] 优先使用静态SQL
- [ ] 使用 `<where>` 代替 `WHERE 1=1`
- [ ] 集合遍历前判空
- [ ] 使用 `#{}` 而非 `${}`
- [ ] 复杂逻辑用 `@SelectProvider`
- [ ] 大集合分批处理

❌ **避免做法**：
- [ ] 过度使用动态SQL
- [ ] 忽略集合空值判断
- [ ] 使用 `${}` 拼接用户输入
- [ ] 在热点查询中使用动态SQL
- [ ] 单次遍历超大集合
- [ ] 过深的标签嵌套（>3层）
