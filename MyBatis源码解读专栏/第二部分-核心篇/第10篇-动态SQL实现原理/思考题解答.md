# 第10篇：动态SQL实现原理 - 思考题解答

## 思考题1：为什么 MyBatis 要设计 SqlNode 树状结构，而不是简单的模板字符串替换？

### 问题分析

这个问题涉及到软件设计的核心思想：**结构化vs字符串拼接**。

### 详细解答

#### 树状结构的优势

**1. 结构化表示，易于理解和维护**

```java
// SqlNode 树状结构
MixedSqlNode root
  ├── StaticTextSqlNode("SELECT * FROM user")
  └── WhereSqlNode
        ├── IfSqlNode(test="name != null")
        │     └── StaticTextSqlNode("AND name = #{name}")
        └── IfSqlNode(test="age != null")
              └── StaticTextSqlNode("AND age > #{age}")
```

```java
// 字符串模板（假设）
String template = "SELECT * FROM user WHERE {% if name != null %}name = #{name}{% endif %} {% if age != null %}AND age > #{age}{% endif %}";
```

**2. 支持条件嵌套和组合**

```xml
<select id="findUsers" resultType="User">
    SELECT * FROM user
    <where>
        <choose>
            <when test="type == 'VIP'">
                <if test="name != null">AND name = #{name}</if>
                AND level >= 5
            </when>
            <otherwise>
                AND status = 'ACTIVE'
            </otherwise>
        </choose>
    </where>
</select>
```

树状结构可以自然表达这种嵌套关系，而字符串模板需要复杂的解析逻辑。

**3. 职责分离，易于扩展**

每个 SqlNode 只负责一种功能：

```java
// 每个节点职责单一
- IfSqlNode: 只负责条件判断
- ForEachSqlNode: 只负责循环遍历
- TrimSqlNode: 只负责前后缀处理

// 扩展新节点很容易
public class CustomSqlNode implements SqlNode {
    @Override
    public boolean apply(DynamicContext context) {
        // 自定义逻辑
    }
}
```

**4. 支持动态组装**

```java
// 可以在运行期动态构建 SqlNode 树
List<SqlNode> nodes = new ArrayList<>();

if (needNameFilter) {
    nodes.add(new IfSqlNode(...));
}

if (needAgeFilter) {
    nodes.add(new IfSqlNode(...));
}

SqlNode root = new MixedSqlNode(nodes);
```

**5. 便于调试和测试**

```java
// 可以单独测试每个节点
@Test
public void testIfSqlNode() {
    SqlNode ifNode = new IfSqlNode(
        new StaticTextSqlNode("AND name = #{name}"),
        "name != null"
    );
    
    DynamicContext context = new DynamicContext(config, params);
    ifNode.apply(context);
    
    assertEquals("AND name = #{name}", context.getSql());
}
```

#### 字符串模板的劣势

**1. 难以处理复杂嵌套**

```java
// 字符串模板处理嵌套很困难
String template = "{% if a %}{% if b %}X{% else %}Y{% endif %}{% else %}Z{% endif %}";
// 需要复杂的解析器
```

**2. 错误定位困难**

```java
// 树状结构：明确知道是哪个节点出错
IfSqlNode at line 10: test expression error

// 字符串模板：只知道位置
Template parse error at position 156
```

**3. 扩展性差**

```java
// 字符串模板添加新语法需要修改解析器
// 树状结构只需要添加新的 SqlNode 实现类
```

### 设计模式分析

SqlNode 树使用了多种设计模式：

**1. 组合模式（Composite Pattern）**

```java
// 统一对待单个节点和节点组合
interface SqlNode {
    boolean apply(DynamicContext context);
}

// 叶子节点
class StaticTextSqlNode implements SqlNode { }

// 组合节点
class MixedSqlNode implements SqlNode {
    private List<SqlNode> contents;  // 可以包含多个子节点
}
```

**2. 访问者模式（Visitor Pattern）**

```java
// DynamicContext 作为访问者，遍历 SqlNode 树
rootSqlNode.apply(context);  // 访问根节点
```

**3. 策略模式（Strategy Pattern）**

```java
// 不同的 SqlNode 代表不同的SQL生成策略
- IfSqlNode: 条件策略
- ForEachSqlNode: 循环策略
- TrimSqlNode: 修剪策略
```

### 实际案例对比

#### 使用树状结构（MyBatis 实现）

```java
// 优雅，易维护
<select id="findUsers" resultType="User">
    SELECT * FROM user
    <where>
        <if test="name != null">AND name = #{name}</if>
        <if test="age != null">AND age > #{age}</if>
    </where>
</select>
```

#### 如果使用字符串模板（假设）

```java
// 笨拙，难维护
String sql = "SELECT * FROM user";
if (!conditions.isEmpty()) {
    sql += " WHERE " + String.join(" AND ", conditions);
}

// 或使用模板引擎
String template = "SELECT * FROM user {{#if hasConditions}}WHERE {{conditions}}{{/if}}";
```

### 总结

SqlNode 树状结构的设计体现了 MyBatis 的以下设计理念：

1. ✅ **结构化优于字符串拼接**
2. ✅ **职责分离，单一职责原则**
3. ✅ **组合优于继承**
4. ✅ **易于扩展（开闭原则）**
5. ✅ **便于测试和调试**

## 思考题2：`<foreach>` 生成的额外参数（如 `__frch_id_0`）为什么要用这种命名方式？直接用原参数有什么问题？

### 问题场景重现

```xml
<select id="findByIds" resultType="User">
    SELECT * FROM user WHERE id IN
    <foreach collection="list" item="id" open="(" separator="," close=")">
        #{id}
    </foreach>
</select>
```

```java
// 调用
List<Long> ids = Arrays.asList(1L, 2L, 3L);
userMapper.findByIds(ids);

// 生成的额外参数
{
  __frch_id_0 = 1L,
  __frch_id_1 = 2L,
  __frch_id_2 = 3L
}
```

### 详细解答

#### 为什么需要重命名？

**问题1：参数名冲突**

```xml
<select id="findUsers" resultType="User">
    SELECT * FROM user WHERE name = #{name}
    AND id IN
    <foreach collection="ids" item="id">
        #{id}  <!-- 这里的 id 和 user.id 冲突了吗？-->
    </foreach>
</select>
```

如果不重命名：

```java
// ParameterHandler 绑定参数时会混淆
ParameterMapping[0].property = "name"   // OK
ParameterMapping[1].property = "id"     // 第1个循环的id
ParameterMapping[2].property = "id"     // 第2个循环的id，与上一个重名！
ParameterMapping[3].property = "id"     // 第3个循环的id，还是重名！
```

**问题2：无法区分迭代变量**

```java
// 循环过程中，id 变量的值在不断变化
for (Object o : iterable) {
    context.bind("id", o);  // 覆盖之前的值
    contents.apply(context);
    // 下一次循环，id 又被覆盖
}

// 最终 context 中只有最后一个值
context.getBindings().get("id") == 3L  // 只剩最后一个
```

**问题3：`#{}`占位符无法定位**

```sql
-- 生成的SQL
SELECT * FROM user WHERE id IN (?, ?, ?)

-- 如果不重命名，ParameterMapping 都是 "id"
ParameterMappings: [id, id, id]

-- ParameterHandler 绑定时，从哪里获取值？
for (int i = 0; i < parameterMappings.size(); i++) {
    String property = parameterMappings.get(i).getProperty();  // 都是 "id"
    Object value = getParameterValue(property);  // 只能获取到最后一个值
    ps.setObject(i + 1, value);
}
```

#### 为什么使用 `__frch_` 前缀？

**1. 避免命名冲突**

```java
// 前缀 __frch_ 确保不会与用户参数冲突
用户参数: {
  id = 100L,
  name = "张三",
  ids = [1, 2, 3]
}

额外参数: {
  __frch_id_0 = 1L,
  __frch_id_1 = 2L,
  __frch_id_2 = 3L
}

// 两者不会冲突
```

**2. 表明来源**

```java
// __frch_ 前缀明确表示这是 foreach 生成的参数
// frch = foreach 的缩写

// 调试时一眼就能看出来源
__frch_id_0    // foreach 生成
__frch_user_1  // foreach 生成
id             // 用户参数
```

**3. 支持嵌套循环**

```xml
<foreach collection="users" item="user">
    <foreach collection="user.orders" item="order">
        #{order.id}
    </foreach>
</foreach>
```

```java
// 内外层循环的参数不会冲突
{
  __frch_user_0 = User(...),
  __frch_user_1 = User(...),
  __frch_order_0 = Order(...),  // 第1个user的订单
  __frch_order_1 = Order(...),
  __frch_order_2 = Order(...),  // 第2个user的订单
}
```

#### 唯一编号的作用

```java
// 源码中的实现
private static String itemizeItem(String item, int i) {
    return ITEM_PREFIX + item + "_" + i;  // "__frch_" + "id" + "_" + 0
}

// 每次循环获取唯一编号
int uniqueNumber = context.getUniqueNumber();  // 0, 1, 2, ...
```

**作用**：

1. **确保参数名唯一**
   ```java
   __frch_id_0  // 唯一
   __frch_id_1  // 唯一
   __frch_id_2  // 唯一
   ```

2. **支持参数正确绑定**
   ```java
   // ParameterHandler 可以准确定位每个参数
   boundSql.hasAdditionalParameter("__frch_id_0")  // true
   boundSql.getAdditionalParameter("__frch_id_0")  // 1L
   ```

3. **避免多线程问题**
   ```java
   // 每次调用都生成新的编号，不会互相干扰
   ```

#### 完整执行流程

```java
// 1. 遍历集合
for (int i = 0; i < ids.size(); i++) {
    Long id = ids.get(i);
    int uniqueNumber = context.getUniqueNumber();  // 0, 1, 2
    
    // 2. 绑定迭代变量
    context.bind("id", id);                        // 临时绑定
    context.bind("__frch_id_" + uniqueNumber, id); // 永久绑定
    
    // 3. 应用子节点（替换占位符）
    contents.apply(new FilteredDynamicContext(...));
    // #{id} -> #{__frch_id_0}
}

// 4. 移除临时绑定
context.getBindings().remove("id");

// 5. 最终额外参数
{
  __frch_id_0 = 1L,
  __frch_id_1 = 2L,
  __frch_id_2 = 3L
}
```

### 如果不使用额外参数会怎样？

**假设直接使用原参数名**：

```java
// 错误的实现（假设）
for (Object o : iterable) {
    context.bind("id", o);  // 每次覆盖
    contents.apply(context);
}

// 生成的SQL
SELECT * FROM user WHERE id IN (?, ?, ?)

// ParameterMappings
[id, id, id]  // 都是同一个名字

// 参数绑定时
for (ParameterMapping pm : parameterMappings) {
    String property = pm.getProperty();  // "id"
    Object value = params.get(property);  // 只能获取到最后一个值
    ps.setObject(i + 1, value);
}

// 结果：三个占位符都绑定了最后一个值！
SELECT * FROM user WHERE id IN (3, 3, 3)  // 错误！
```

### 其他ORM框架的做法

**Hibernate HQL**：

```java
// 使用位置参数
Query query = session.createQuery("FROM User WHERE id IN (:ids)");
query.setParameterList("ids", Arrays.asList(1, 2, 3));

// 内部也会展开为多个参数
```

**JPA Criteria API**：

```java
// 使用 in() 方法
CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery<User> query = cb.createQuery(User.class);
Root<User> root = query.from(User.class);
query.where(root.get("id").in(ids));
```

### 总结

使用 `__frch_` 前缀和唯一编号的原因：

1. ✅ **避免参数名冲突**：与用户参数隔离
2. ✅ **支持正确绑定**：每个参数都有唯一标识
3. ✅ **便于调试**：一眼看出参数来源
4. ✅ **支持嵌套循环**：多层循环不会互相干扰
5. ✅ **明确语义**：表明参数的特殊性

这是 MyBatis 为了正确处理动态SQL而设计的巧妙机制！

## 思考题3：在什么场景下应该使用 `<bind>`，而不是在 Java 代码中处理参数？

### 问题分析

`<bind>` 标签允许在 XML 中使用 OGNL 表达式创建新变量。这个问题涉及到 **职责分离** 和 **代码组织** 的权衡。

### 详细解答

#### `<bind>` 的典型使用场景

**场景1：模糊查询**

```xml
<!-- ✅ 推荐：使用 <bind> -->
<select id="findByName" resultType="User">
    <bind name="pattern" value="'%' + name + '%'"/>
    SELECT * FROM user WHERE name LIKE #{pattern}
</select>
```

```java
<!-- ❌ 不推荐：Java代码处理 -->
// Mapper接口
List<User> findByName(String name);

// 调用时
userMapper.findByName("%" + name + "%");  // 调用方需要知道内部实现细节
```

**优势**：
- ✅ 封装实现细节：调用方不需要知道是模糊查询
- ✅ 防止错误：调用方不会忘记加 `%`
- ✅ 集中管理：所有SQL逻辑都在XML中

---

**场景2：日期范围查询**

```xml
<!-- ✅ 推荐：使用 <bind> -->
<select id="findByDateRange" resultType="Order">
    <bind name="startDate" value="date + ' 00:00:00'"/>
    <bind name="endDate" value="date + ' 23:59:59'"/>
    
    SELECT * FROM `order`
    WHERE created_at BETWEEN #{startDate} AND #{endDate}
</select>
```

```java
// ❌ 不推荐：Java代码处理
public List<Order> findByDateRange(String date) {
    String startDate = date + " 00:00:00";
    String endDate = date + " 23:59:59";
    return orderMapper.findByDateRange(startDate, endDate);
}
```

**优势**：
- ✅ 语义清晰：一眼看出日期范围的构造方式
- ✅ 复用方便：多个SQL可以共享同样的逻辑
- ✅ 类型安全：OGNL会进行类型检查

---

**场景3：动态拼接多个条件**

```xml
<!-- ✅ 推荐：使用 <bind> -->
<select id="findUsers" resultType="User">
    <bind name="hasConditions" value="name != null or age != null or status != null"/>
    
    SELECT * FROM user
    <if test="hasConditions">
        WHERE 1=1
        <if test="name != null">AND name = #{name}</if>
        <if test="age != null">AND age > #{age}</if>
        <if test="status != null">AND status = #{status}</if>
    </if>
</select>
```

**优势**：
- ✅ 减少重复：避免在多个 `<if>` 中重复判断
- ✅ 提升性能：表达式只求值一次
- ✅ 易于维护：条件变化时只需修改一处

---

**场景4：计算派生值**

```xml
<!-- ✅ 推荐：使用 <bind> -->
<select id="findByPriceRange" resultType="Product">
    <bind name="minPrice" value="price * (1 - discount)"/>
    <bind name="maxPrice" value="price * (1 + margin)"/>
    
    SELECT * FROM product
    WHERE price BETWEEN #{minPrice} AND #{maxPrice}
</select>
```

**优势**：
- ✅ 业务逻辑可见：折扣和利润率的计算逻辑在SQL中可见
- ✅ 避免重复计算：Java层不需要再计算
- ✅ 便于测试：可以单独测试SQL

---

#### 应该在 Java 代码中处理的场景

**场景1：复杂的业务逻辑**

```java
// ✅ 推荐：Java代码处理
public List<User> findByComplexCondition(UserQuery query) {
    // 复杂的业务规则
    String status = calculateStatus(query);
    Integer level = calculateLevel(query);
    Date validDate = calculateValidDate(query);
    
    return userMapper.findByCondition(status, level, validDate);
}
```

```xml
<!-- ❌ 不推荐：<bind> 处理复杂逻辑 -->
<select id="findUsers" resultType="User">
    <bind name="status" value="@com.example.Utils@calculateStatus(_parameter)"/>
    <!-- OGNL调用静态方法，不直观，难维护 -->
</select>
```

**原因**：
- ❌ OGNL表达式复杂度有限
- ❌ 难以调试和测试
- ❌ 违反单一职责原则

---

**场景2：需要访问外部服务**

```java
// ✅ 推荐：Java代码处理
public List<Order> findByUser(Long userId) {
    User user = userService.getUser(userId);  // 调用其他服务
    String region = user.getRegion();
    return orderMapper.findByRegion(region);
}
```

```xml
<!-- ❌ 不可能：<bind> 无法调用服务 -->
<select id="findOrders" resultType="Order">
    <bind name="region" value="..."/>  <!-- 无法访问Spring Bean -->
</select>
```

---

**场景3：需要异常处理**

```java
// ✅ 推荐：Java代码处理
public List<User> findByDateRange(String dateStr) {
    try {
        Date date = DateFormat.parse(dateStr);
        return userMapper.findByDate(date);
    } catch (ParseException e) {
        throw new IllegalArgumentException("Invalid date format", e);
    }
}
```

```xml
<!-- ❌ 不推荐：<bind> 无法优雅处理异常 -->
<bind name="date" value="@DateFormat@parse(dateStr)"/>
<!-- 解析失败会抛出运行时异常，难以控制 -->
```

---

#### 决策树

```
是否使用 <bind>？
│
├─ 是否是SQL相关的简单逻辑？
│  ├─ 是 → 使用 <bind>
│  │     ├─ 字符串拼接（模糊查询）
│  │     ├─ 简单计算（日期范围、价格范围）
│  │     ├─ 条件变量（减少重复判断）
│  │     └─ 参数转换（类型转换）
│  │
│  └─ 否 → 使用 Java 代码
│        ├─ 复杂业务逻辑
│        ├─ 需要调用其他服务
│        ├─ 需要异常处理
│        └─ 需要事务控制
│
└─ 是否影响SQL可读性？
   ├─ 否 → 使用 <bind>
   └─ 是 → 使用 Java 代码
```

#### 最佳实践对比

| 维度 | `<bind>` | Java代码 |
|------|----------|---------|
| **简单字符串拼接** | ✅ 推荐 | ❌ 不推荐 |
| **简单数值计算** | ✅ 推荐 | ⚠️ 可以 |
| **复杂业务逻辑** | ❌ 不推荐 | ✅ 推荐 |
| **需要调用服务** | ❌ 不可能 | ✅ 推荐 |
| **需要异常处理** | ❌ 困难 | ✅ 推荐 |
| **需要单元测试** | ⚠️ 困难 | ✅ 容易 |
| **SQL可读性** | ✅ 集中管理 | ⚠️ 分散 |

#### 实际案例

**案例1：用户搜索功能**

```xml
<!-- ✅ 好的设计 -->
<select id="searchUsers" resultType="User">
    <!-- 使用 <bind> 处理简单的字符串拼接 -->
    <bind name="namePattern" value="'%' + name + '%'"/>
    <bind name="emailPattern" value="'%' + email + '%'"/>
    
    SELECT * FROM user
    <where>
        <if test="name != null">AND name LIKE #{namePattern}</if>
        <if test="email != null">AND email LIKE #{emailPattern}</if>
        <if test="status != null">AND status = #{status}</if>
    </where>
</select>
```

```java
// ✅ Java层处理复杂逻辑
public List<User> searchUsers(UserSearchQuery query) {
    // 1. 参数校验
    validateQuery(query);
    
    // 2. 权限检查
    checkPermission(query);
    
    // 3. 调用Mapper
    return userMapper.searchUsers(query.getName(), query.getEmail(), query.getStatus());
}
```

### 总结

**使用 `<bind>` 的黄金法则**：

1. ✅ **简单的SQL相关逻辑** → 使用 `<bind>`
   - 字符串拼接（`'%' + name + '%'`）
   - 简单计算（`price * 0.9`）
   - 条件变量（`name != null or email != null`）

2. ❌ **复杂的业务逻辑** → 使用 Java 代码
   - 需要调用其他服务
   - 需要异常处理
   - 需要事务控制
   - 需要复杂计算

3. 🎯 **职责分离原则**：
   - **XML层**：专注于SQL查询逻辑
   - **Java层**：处理业务逻辑和流程控制

4. 📊 **可维护性优先**：
   - 如果 `<bind>` 让SQL更难理解 → 用Java代码
   - 如果Java代码让调用方更复杂 → 用 `<bind>`

## 思考题4：如何设计一个插件来缓存动态SQL的解析结果，以提升性能？

### 问题分析

动态SQL的性能瓶颈在于**每次执行都要重新解析**。设计缓存插件需要考虑：
1. 缓存什么？
2. 缓存键如何生成？
3. 何时失效？
4. 线程安全？

### 详细解答

#### 设计思路

**核心思想**：缓存 `DynamicContext` 生成的 SQL 文本和参数绑定。

#### 完整实现

```java
/**
 * 动态SQL缓存插件
 * 
 * 拦截 MappedStatement.getBoundSql 方法
 */
@Intercepts({
    @Signature(
        type = MappedStatement.class,
        method = "getBoundSql",
        args = {Object.class}
    )
})
public class DynamicSqlCachePlugin implements Interceptor {
  
    /**
     * SQL缓存
     * Key: statementId + 参数特征
     * Value: 缓存的BoundSql信息
     */
    private final Cache<String, CachedSql> sqlCache;
  
    public DynamicSqlCachePlugin() {
        // 使用Caffeine实现LRU缓存
        this.sqlCache = Caffeine.newBuilder()
            .maximumSize(1000)                    // 最大1000条
            .expireAfterWrite(1, TimeUnit.HOURS)  // 1小时过期
            .recordStats()                        // 记录统计信息
            .build();
    }
  
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        MappedStatement ms = (MappedStatement) invocation.getTarget();
        Object parameterObject = invocation.getArgs()[0];
      
        // 1. 判断是否需要缓存
        if (!shouldCache(ms)) {
            return invocation.proceed();
        }
      
        // 2. 生成缓存键
        String cacheKey = generateCacheKey(ms, parameterObject);
      
        // 3. 尝试从缓存获取
        CachedSql cachedSql = sqlCache.getIfPresent(cacheKey);
        if (cachedSql != null) {
            // 缓存命中，直接返回
            return cachedSql.toBoundSql(ms.getConfiguration(), parameterObject);
        }
      
        // 4. 缓存未命中，执行原方法
        BoundSql boundSql = (BoundSql) invocation.proceed();
      
        // 5. 缓存结果
        sqlCache.put(cacheKey, CachedSql.from(boundSql));
      
        return boundSql;
    }
  
    /**
     * 判断是否应该缓存
     */
    private boolean shouldCache(MappedStatement ms) {
        // 只缓存动态SQL
        return ms.getSqlSource() instanceof DynamicSqlSource;
    }
  
    /**
     * 生成缓存键
     * 
     * 关键：要能反映参数对SQL结构的影响
     */
    private String generateCacheKey(MappedStatement ms, Object parameterObject) {
        StringBuilder keyBuilder = new StringBuilder();
      
        // 1. Statement ID
        keyBuilder.append(ms.getId());
        keyBuilder.append(":");
      
        // 2. 参数结构特征（不包含参数值）
        if (parameterObject == null) {
            keyBuilder.append("null");
        } else if (parameterObject instanceof Map) {
            Map<?, ?> paramMap = (Map<?, ?>) parameterObject;
          
            // Map参数：使用key集合作为特征
            keyBuilder.append("map:");
            keyBuilder.append(String.join(",", 
                paramMap.keySet().stream()
                    .map(Object::toString)
                    .sorted()
                    .collect(Collectors.toList())
            ));
          
            // 关键：哪些key有值，哪些为null
            keyBuilder.append(":");
            keyBuilder.append(String.join(",",
                paramMap.entrySet().stream()
                    .filter(e -> e.getValue() != null)
                    .map(e -> e.getKey().toString())
                    .sorted()
                    .collect(Collectors.toList())
            ));
        } else {
            // POJO参数：使用类名和非null属性名作为特征
            MetaObject metaObject = ms.getConfiguration().newMetaObject(parameterObject);
            String[] getterNames = metaObject.getGetterNames();
          
            keyBuilder.append(parameterObject.getClass().getName());
            keyBuilder.append(":");
            keyBuilder.append(String.join(",",
                Arrays.stream(getterNames)
                    .filter(name -> metaObject.getValue(name) != null)
                    .sorted()
                    .collect(Collectors.toList())
            ));
        }
      
        return keyBuilder.toString();
    }
  
    /**
     * 缓存的SQL信息
     */
    private static class CachedSql {
        private final String sql;
        private final List<String> parameterProperties;  // 参数属性名列表
        private final List<JdbcType> jdbcTypes;
        private final List<Class<?>> javaTypes;
      
        public static CachedSql from(BoundSql boundSql) {
            List<ParameterMapping> parameterMappings = boundSql.getParameterMappings();
          
            return new CachedSql(
                boundSql.getSql(),
                parameterMappings.stream()
                    .map(ParameterMapping::getProperty)
                    .collect(Collectors.toList()),
                parameterMappings.stream()
                    .map(ParameterMapping::getJdbcType)
                    .collect(Collectors.toList()),
                parameterMappings.stream()
                    .map(ParameterMapping::getJavaType)
                    .collect(Collectors.toList())
            );
        }
      
        public BoundSql toBoundSql(Configuration configuration, Object parameterObject) {
            // 重建 ParameterMapping 列表
            List<ParameterMapping> parameterMappings = new ArrayList<>(parameterProperties.size());
            for (int i = 0; i < parameterProperties.size(); i++) {
                ParameterMapping pm = new ParameterMapping.Builder(
                    configuration,
                    parameterProperties.get(i),
                    javaTypes.get(i)
                )
                .jdbcType(jdbcTypes.get(i))
                .build();
              
                parameterMappings.add(pm);
            }
          
            // 创建 BoundSql
            return new BoundSql(configuration, sql, parameterMappings, parameterObject);
        }
      
        // 构造函数和getter省略
    }
  
    @Override
    public Object plugin(Object target) {
        return Plugin.wrap(target, this);
    }
  
    @Override
    public void setProperties(Properties properties) {
        // 可以从配置文件读取缓存参数
    }
  
    /**
     * 获取缓存统计信息
     */
    public CacheStats getStats() {
        return sqlCache.stats();
    }
}
```

#### 关键设计决策

**1. 缓存键的设计**

```java
// ✅ 好的缓存键：反映SQL结构
"UserMapper.findUsers:map:age,name:age,name"
// statementId + 参数类型 + 有值的参数

// ❌ 差的缓存键：包含参数值

// 不同参数值会生成不同的键，缓存命中率低
```

**2. 缓存内容的选择**

```java
// ✅ 缓存SQL文本和ParameterMapping信息
class CachedSql {
    String sql;
    List<String> parameterProperties;
    // ...
}

// ❌ 缓存整个BoundSql对象
// BoundSql包含parameterObject，会导致内存泄漏
```

**3. 线程安全**

```java
// ✅ 使用线程安全的缓存实现
private final Cache<String, CachedSql> sqlCache = 
    Caffeine.newBuilder().build();

// ❌ 使用HashMap
private final Map<String, CachedSql> sqlCache = new HashMap<>();
// 多线程环境下会出问题
```

## 思考题5：对于包含大量 `<if>` 条件的复杂动态SQL，如何进行性能优化？

### 问题场景

```xml

    <where>
        <if test="name != null">AND name = #{name}</if>
        <if test="email != null">AND email = #{email}</if>
        <if test="phone != null">AND phone = #{phone}</if>
        <if test="minAge != null">AND age >= #{minAge}</if>
        <if test="maxAge != null">AND age <= #{maxAge}</if>
        <if test="status != null">AND status = #{status}</if>
```

### 性能问题分析

**1. 动态SQL解析开销**

```

1. 创建 DynamicContext
2. 求值 10 个 OGNL 表达式
3. 拼接 SQL 片段
4. 解析 #{} 占位符
5. 生成 ParameterMapping

总耗时：~50-100μs
```

**2. 数据库执行计划不稳定**

```sql

-- 查询优化器难以缓存执行计划

-- 组合1

-- 组合2

-- 组合3
```

### 优化方案

#### 方案1：拆分多个静态SQL（推荐）

**优化思路**：识别高频查询组合，拆分为独立的静态SQL。

```xml

    <!-- 10个<if>条件 -->
</select>

<!-- 拆分后：多个静态SQL -->

</select>

<!-- 场景2：按姓名+年龄查询（30%流量） -->

<select id="findByStatus" resultType="User">
    SELECT * FROM user WHERE status = #{status}
</select>

<!-- 场景4：复杂查询（10%流量） -->
```

- 覆盖90%的流量

#### 方案2：使用 `@SelectProvider` + 缓存

**优化思路**：编程式构建SQL，缓存构建结果。

```java
public class UserSqlProvider {
  
    /**
     * SQL构建结果缓存
     * Key: 参数结构特征
     * Value: 构建的SQL
     */
    private static final Map<String, String> SQL_CACHE = new ConcurrentHashMap<>();
  
    public String searchUsers(Map<String, Object> params) {
        // 1. 生成缓存键
        String cacheKey = generateCacheKey(params);
      
        // 2. 从缓存获取
        return SQL_CACHE.computeIfAbsent(cacheKey, k -> buildSql(params));
    }
  
    private String buildSql(Map<String, Object> params) {
        StringBuilder sql = new StringBuilder("SELECT * FROM user WHERE 1=1");
      
        // 3. 按优先级构建条件（索引优先）
        if (params.get("name") != null) {
            sql.append(" AND name = #{name}");
        }
        if (params.get("status") != null) {
            sql.append(" AND status = #{status}");
        }
        if (params.get("minAge") != null) {
            sql.append(" AND age >= #{minAge}");
        }
        if (params.get("maxAge") != null) {
            sql.append(" AND age <= #{maxAge}");
        }
        // ... 其他条件
      
        return sql.toString();
    }
  
    private String generateCacheKey(Map<String, Object> params) {
        // 生成参数结构特征
        return params.keySet().stream()
            .filter(key -> params.get(key) != null)
            .sorted()
            .collect(Collectors.joining(","));
    }
}
```

```java

```

**性能提升**：
- 第一次：构建SQL（慢）
- 后续：从缓存获取（快）
- 性能提升：100-150%

优化复杂动态SQL的黄金法则：

6. ✅ **减少重复求值** → 使用 `<bind>`

1. 先数据库优化（索引）
2. 再拆分静态SQL
3. 最后应用层缓存
