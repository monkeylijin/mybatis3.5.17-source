# 第11篇：思考题解答（插件系统）

## 思考题 1：MyBatis 插件系统是如何实现无侵入式扩展的？

核心机制是两点：

1. **对象创建时统一代理**：`Configuration` 在创建四大接口实现类对象时调用 `InterceptorChain.pluginAll()`，把对象替换为代理对象。
2. **方法调用时回调插件逻辑**：代理对象在匹配 `@Signature` 声明的方法调用时，回调 `Interceptor.intercept()`，由插件决定是否继续执行 `Invocation.proceed()`。

因此，插件不需要修改 MyBatis 内部实现类，就能对关键方法做前置/后置处理或改变返回值。

## 思考题 2：`Plugin.wrap()` 方法是如何选择需要代理的接口的？

`Plugin.wrap()` 会：

1. 从插件类 `@Intercepts` 解析出一个 `signatureMap`：key 是接口类型（如 `Executor.class`），value 是该接口上被声明拦截的方法集合
2. 遍历目标对象的 class 及其父类，收集其实现的接口
3. 只把那些“存在于 signatureMap key 集合中”的接口加入代理接口列表

如果最终接口列表为空，说明该插件对这个 target 没有任何可拦截的方法，直接返回原对象，避免无意义代理。

## 思考题 3：多个插件的执行顺序如何确定？如何控制？

执行顺序由 `InterceptorChain.pluginAll()` 的 wrap 顺序决定：

- 注册顺序：A -> B -> C
- wrap 过程：`target = A.plugin(target)`；再 `target = B.plugin(target)`；再 `target = C.plugin(target)`
- 最终得到的对象最外层是 C 的代理，因此调用发生时通常会先进入 C 的 `intercept()`，然后 `proceed()` 才会进入 B，再进入 A，最后到真实对象。

如何控制：

- 通过调整 `mybatis-config.xml` 中 `<plugins>` 的顺序控制注册顺序
- 需要特别注意：插件之间如果会修改参数、SQL、返回值，顺序变化就可能导致语义变化

## 思考题 4：为什么插件只能拦截这四个接口？

原因包含设计与实现两层：

- 设计层：四大接口覆盖一次 SQL 执行的关键阶段，作为官方扩展点更稳定、更可控
- 实现层：`Invocation` 构造函数会校验 `method.getDeclaringClass()` 是否属于四大接口之一，否则直接抛 `IllegalArgumentException`，形成硬边界

这保证了插件能力不会无限扩张，MyBatis 也能对插件体系的语义与性能做基本保障。

## 思考题 5：如何实现一个支持多数据库的分页插件？

思路分两步：

1. 选择拦截点：通常拦截 `StatementHandler.prepare(...)`（物理分页）或 `Executor.query(...)`（逻辑分页/改参数）
2. 方言抽象：把 “SQL 改写规则” 抽象为 Dialect（MySQL/PostgreSQL/Oracle...）

实现建议：

- 插件配置支持 `dialect=mysql|postgres`，或根据 JDBC URL/DatabaseMetaData 自动识别
- 物理分页需要改写 SQL 并绑定参数（LIMIT/OFFSET 的写法不同），要注意 `BoundSql.sql` 不可直接 set，反射修改存在版本兼容风险
- 如果只是学习演示，可用 `RowBounds` 做逻辑分页，避免改 SQL 的复杂度
